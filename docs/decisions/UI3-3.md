# UI3-3 — Rules, Requests and Program setup in design v3 (D-520 to D-529)

**D-520 — Two hairline columns for Rules and Program setup, the list's selection bleeding into the gutter.** Both
screens put a list beside the thing it opens: Rules' versions beside the chosen version, Program setup's steps beside
the open step. Each is now two columns under one hairline, divided by a vertical hairline, with no sunken panel, framed
pane or card (UI3-0's "framed two-pane panel"). The list column is 280 px of text (Rules) or 200 px (setup); its rows
carry 12 px of inset that sits in the page's gutter (`margin-left: -12px`), so every word in the list aligns with the
title above it while the hover, selection and active backgrounds still have room. The list is sticky beside a long
detail. Under 1024 px (Rules) and 900 px (setup) the list moves above at its full height (a scroll area cut its last
row through the middle at 400 px), a hairline between. Rejected: the 12 px inset
inside the column (the words would sit 12 px right of the title); a card per pane (the v2 failure DESIGN.md names).

**D-521 — Rule version and request statuses borrow the mark table's shapes; the word says which.** DESIGN.md allows a
status only as a mark plus a word, and its table has seven shapes. A rule version's five statuses take five of them:
Approved the filled disc (a person accepted the list) drawn in `ink`, Needs approval the outline ring (not reviewed),
Extracting the ring with a centre dot (waiting on another party, the model), Extraction failed the filled square in
`missing` (an error, which a reviewer must act on), Superseded the dashed ring (outdated). Approval is not evidence, so
it never borrows `found` (orchestrator review): StatusMark takes an optional `tone` for a borrowed shape, and `ink` is
that tone's only value outside the table. `rules.spec.ts` proves no two statuses share a shape, that Approved is drawn in
`ink`, that none is `found` and that only Extraction failed is `missing`; `status-mark.spec.ts` covers the override. A
request is Open (ring with dot, evidence requested), Answered (outline ring: the answer waits for the reviewer) or
Blocked (outline square). Passing the borrowed `Status` with a `label` uses StatusMark as it is; no local copy and no
new shape. Rejected: Labels for statuses (UI3-0's interim; a Label is for an attribute, not a state); a mark for
Answered in `found` (it would read as evidence found, which only a reviewer may conclude).

**D-522 — An approved version's state line is one mark and one sentence.** "Approved" next to "Approved by Dr. Priya
Raman on 2026-11-27" said the word twice. An approved version shows the mark with the sentence as its words; every other
status shows its mark and word, then " · " and "Not approved" or who approved it (a superseded version). The date stays
ISO, as the version's effective date beside it is. The version's facts (state, license, effective date, source) are one
meta line under the label; the requirement count moved from a Figure to the Requirements tab, in meta type, since the
column has one focal point, the label.

**D-523 — The requirement list as four columns, aligned on the first baseline.** Six columns did not fit the 830 px detail
column (the search terms were cut off in UI3-0's screenshot and the table scrolled sideways). Type and check move under
the title as one meta line ("Numeric · Internship hours >= 700"), leaving Ref, Requirement, Text and Search terms. The
ref is Inter tabular 500 and the check tabular Inter, not mono (DESIGN.md keeps mono for hashes and offsets). The text
is Document type, three lines until "Show all". Cells align on the first line's baseline, so Body, Document and Labels
share a line. It is a semantic `lx-table` (no sorting or paging), so it is named by `aria-label` directly. Under 720 px
each requirement is a block.

**D-524 — Search terms are Labels everywhere, including the chips being edited.** The read-only cell lists each term as
a Label. The edit grid keeps PrimeNG AutoComplete for entering them; its chips are drawn as Labels (20 px, a
`line-strong` outline, `ink-2` meta text, no fill) by the Rules stylesheet, since the chip token set has no border.
Compare's search-term aspect shows the terms as Labels too, a removed one struck through in `missing`, an added one
underlined in `found`, with "removed:" and "added:" for screen readers.

**D-525 — The diff: inserted text underlined in `found`, deleted text struck through in `missing`, all in Document type.**
The roadmap asks for "found and missing underlines". Deleted text is drawn with a line through it rather than under it:
an underline in two colours would make colour the only difference between an insertion and a deletion, which DESIGN.md
forbids, and a struck-through deletion is how a legal redline reads. This is the shared `DiffText`, unchanged. Old and
new values of a title, type, check or ref now sit side by side as deleted and inserted text with "becomes" for screen
readers; the arrow icons are gone. Added requirements' text is wholly inserted, removed ones' wholly deleted, unchanged
ones plain in `ink-2`. The summary is one sentence of numerals and words; the counts' sunken pills and status icons are
gone. What changed comes first (orchestrator review): changed, added and removed requirements are listed, and the
unchanged ones wait behind one text button, "Show 8 unchanged" (`aria-expanded`, controlling their own row group),
collapsed by default and remembered for the session in a module signal; the rule-text diff follows right under them.

**D-526 — The answer drawer is an overlay sheet: floating, faded in, one radius.** The shared `Sheet` keeps PrimeNG
Drawer for focus trapping and its own backdrop (D-265), but now floats 12 px inside the window with the overlay radius
(8 px) and the overlay elevation, and enters as every overlay does, fading in and rising 4 px over 150 ms (the drawer's
0.5 s slide is replaced on its enter and leave classes); under 1024 px it fills the window, as the end-to-end test
expects. Its heading is Section type (it was 20 px, outside the scale). Inside, the requirement is set as Review sets it
(the rule text in Document type on a 2 px `line-strong` rule) and a hairline separates it from the three numbered
parts; the sunken inset, the card around the note and the avatars are gone. The Sheet is shared with Program setup's
document and fact sheets, which take the same look; the report's `.lx-sheet` article is a different element and is not
touched.

**D-527 — Program setup: a numbered text list, plain forms and tables.** The PrimeNG Stepper stays for its value and
steps, laid out as the left column: each step a 52 px row of the number (tabular `ink-2`), the name (UI type) and its
summary (meta), the open step in `ink` on `sunken` with a 2 px `ink` rule at its left, the way the rail marks its
screen. No discs, no check icons, no separators. Under 900 px the steps become a grid of numbered names (three across,
two under 640 px) above the step, their summaries in their accessible names. Details is a definition list on 40 px rows;
States a table; Courses a table with one text action; Documents one table grouped by course (a row group per course,
"No syllabus yet" where a course has none) in place of the grid of sunken cards, with a single dashed drop zone above
it; Program facts one row per number between hairlines (name, value in tabular figures, the quote in Document type, one
text action) in place of cards; no file or lock icons.

**D-528 — The readiness checklist has its own neutral check and cross.** A requirement's status marks mean findings and
decisions; a readiness line is neither. Each line is now a Phosphor check (done, `ink-2`) or cross (open: `ink` when it
blocks the run, `ink-2` when it does not), its sentence, and for an open line the words "Blocks the run" or "Does not
block" and its fix as a text action ("Open Rules", "Open Documents", "Open Program facts" instead of "Fix"). Nothing is
coloured: whether a line blocks is said in words. `checkState` (done, blocking, warning) moved into `setup-model.ts`
with a unit test, and the line's `data-state` replaces `data-tone` in `setup.spec.ts`. The run is a plain row: its
status, the Meter with "12 of 16 requirements assessed", and "Open Review"; the framed progress card is gone.

**D-529 — Live regions, filters and row actions follow the overview.** Rules and Requests now say a result to assistive
technology through a hidden live region (`data-testid="message"`, as Program setup and Coverage already did) and on
screen through the toast, so an empty 32 px status line no longer sits under the title. The request filter stays a
SelectButton (a toggle group is the right semantics for a filter, and the end-to-end tests address it), drawn as an
underlined text row with counts in meta type, like the tab rows. Row actions that open something (Provide evidence, New
catalog year, Record) are accent text actions as on the overview, keeping their accessible names; only a screen's
primary action is a filled button (New rule version, Run assessment, both 36 px).
